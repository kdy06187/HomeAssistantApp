3코드 해설

① 토스트를 MainActivity 한 곳에서 (#5·#6)

BEFORE · DeviceFragment
viewModel.getToastMessage().observe(..., message -> {
    Toast.makeText(getContext(), message, ...).show();
});
// HomeFragment에는 이 코드가 없음
AFTER · MainActivity
viewModel.getToastMessage().observe(this, event -> {
    String message = event != null
        ? event.takeIfNotHandled() : null;
    if (message != null) Toast.makeText(...).show();
});
무엇을 하나 · ViewModel이 내보낸 토스트를 화면 틀(Activity)에서 띄웁니다. 그래서 어느 탭에 있든 보입니다.
왜 이렇게 했나 · HomeFragment에도 관찰을 하나 더 붙일 수도 있었습니다. 하지만 LiveData는 새로 관찰을 시작한 쪽에 마지막 값을 다시 줍니다. 그러면 탭을 바꿀 때마다 예전 토스트가 다시 뜹니다. 그래서 한 곳에서, OneTimeEvent로 감싸 한 번만 띄웁니다.
빼면 · 대시보드에서 "제어 실패: 명령 실패!"가 다시 보이지 않습니다. 실서버 확인에서 실제로 나온 증상이 이것입니다.

스위치가 원래 자리로 돌아가는 것은 정상입니다. 누르는 순간 LOADING이 되고, 실패 응답이 오면 서버가 알려 준 현재 상태(꺼짐/오프라인)로 다시 그립니다.

재확인 결과: 이제 대시보드에서도 토스트가 뜹니다(앱 OK). 그런데 문구가 "명령 성공!"입니다. 원인은 서버입니다. 등록된 기기면 실제 제어가 실패해도 성공(true)을 돌려주고 상태만 OFFLINE으로 바꿉니다. 앱은 서버가 준 대로 보여 줄 뿐이라 서버 v2.0에서 고칩니다. 이렇게 앱 문제와 서버 문제를 나눠 보는 것이 팀 간 협업의 핵심입니다.

② 401이면 요청별 실패 토스트를 건너뜀 (#2)

BEFORE
toastMessage.setValue("전력 조회 실패: "
    + ErrorMessages.describe(response));
AFTER
private void showFailure(String prefix, Response<?> r) {
    if (ErrorMessages.isUnauthorized(r.code())) return;
    showToast(prefix + ErrorMessages.describe(r));
}
무엇을 하나 · 401 응답이면 그 요청의 실패 토스트를 띄우지 않습니다. 토큰 안내는 UnauthorizedInterceptor → MainActivity가 한 번만 합니다.
왜 이렇게 했나 · 원인이 하나(토큰)인데 요청마다 토스트를 띄우면 화면이 시끄럽고, 사용자는 진짜 원인을 놓칩니다. 실패 토스트를 showFailure 한 곳으로 모았으니 규칙도 한 줄로 끝납니다.
빼면 · 기기 관리 탭에서 "목록 로드 실패: 인증이 필요합니다."와 "API 토큰이 맞지 않습니다…"가 함께 떠서 2번이 됩니다.

②-2 늦게 온 401도 안내는 한 번 (#2 재수정)

기기 관리 탭에 들어가면 목록 조회와 기기별 상태 조회가 한꺼번에 나갑니다. 토큰이 틀리면 401이 시간 차를 두고 여러 번 옵니다. 예전 플래그는 MainActivity가 안내를 띄우며 내려 버려서, 늦게 온 401이 플래그를 다시 올렸습니다.

BEFORE · RetrofitClient
if (unauthorizedPending.compareAndSet(false, true)) {
    unauthorizedSignal.postValue(true);
}
// MainActivity가 consume → false로 내림
// → 늦게 온 401이 또 true로 올림
AFTER
if (!unauthorizedNotice.tryClaim()) return;
unauthorizedPending.set(true);
unauthorizedSignal.postValue(true);
// SettingsFragment 저장 때만
// resetUnauthorizedNotice()
무엇을 하나 · 플래그가 두 개입니다. unauthorizedPending은 "아직 화면이 처리 안 함"(화면 회전 때 다시 뜨지 않게)이고, UnauthorizedNotice는 "이번 설정으로는 이미 안내함"입니다.
왜 이렇게 했나 · "몇 초 동안만 막기"는 시간이 길어지면 또 뜨고, 테스트도 시간에 기대게 됩니다. 사용자가 행동(설정 저장)을 해야 안내를 되살리는 쪽이 규칙이 분명합니다.
빼면 · 기기 수만큼 늦게 온 401이 같은 토큰 안내를 또 띄웁니다(재확인에서 2번이 나온 이유).

③ PendingStates — 로딩은 반드시 끝난다 (#11)

BEFORE
final String previousState = findState(id);
// 이미 LOADING이면 null을 기억함
updateDevice(id, d -> d.setState("LOADING"));
...
onFailure: d.setState(previousState);
AFTER
beginLoading(id);   // 요청 수 +1, 실제 상태 기억
...
onFailure: finishLoading(id, null);
// 남은 요청이 있으면 LOADING,
// 없으면 마지막 실제 상태
무엇을 하나 · 기기마다 "진행 중인 요청 수"를 셉니다. 0이 되는 순간 LOADING 대신 마지막으로 알던 실제 상태(ON/OFF/OFFLINE…)를 보여 줍니다.
왜 이렇게 했나 · 대시보드가 화면에 돌아오면 전력과 기록 요청이 동시에 나갑니다. 두 번째 요청은 시작할 때 이미 LOADING이라 되돌릴 상태가 없었습니다(null). 요청 수를 세면 순서와 상관없이 마지막 요청이 끝날 때 바른 상태로 돌아옵니다.
빼면 · 요청이 겹칠 때 상태가 null("알 수 없음")로 남거나, 먼저 끝난 요청이 다른 요청이 아직 진행 중인데도 로딩을 풀어 버립니다.

재확인 결과: OK. 로딩이 풀리고 "제어 에러" 토스트가 뜹니다.

또 하나: 서버 PC가 꺼져 있으면 연결 요청에 아무도 답하지 않아서, 앱이 연결 타임아웃(예전 60초)까지 로딩을 보여 줬습니다. 같은 집 LAN에서는 연결이 1초도 안 걸리므로 10초로 줄였습니다. 기기 등록처럼 오래 걸리는 것은 "읽기" 시간이라 이 변경과 상관없습니다.

4용어 풀이

  • LiveData 재전달: 새로 관찰을 시작한 쪽에 마지막 값을 곧바로 다시 주는 성질입니다. 화면 상태에는 좋지만 토스트처럼 "한 번만" 보여야 하는 값에는 문제가 됩니다.
  • 일회성 이벤트(OneTimeEvent): 값을 상자에 담고, 처음 꺼낼 때만 내주는 방식입니다.
  • 401 Unauthorized: 토큰이 없거나 틀렸다는 HTTP 응답 코드입니다.
  • 연결 타임아웃 / 읽기 타임아웃: 서버와 연결을 맺기까지 기다리는 시간과, 연결된 뒤 응답을 기다리는 시간입니다.
  • 참조 카운트: "지금 몇 개가 쓰고 있나"를 세어 0이 될 때 정리하는 방법입니다. PendingStates가 이 방식을 씁니다.

정답 
@Test
public void middleSuccess_isKeptAfterLastFailure() {
    PendingStates states = new PendingStates();
    states.begin("A", "ON");
    states.begin("A", PendingStates.LOADING);
    states.begin("A", PendingStates.LOADING);
    assertEquals(PendingStates.LOADING, states.finish("A", null));
    assertEquals(PendingStates.LOADING, states.finish("A", "OFF"));
    assertEquals("OFF", states.finish("A", null));
}

실습 2 · 서버 연결 실패도 한 번만 알리기

  • 목표: 서버가 꺼져 있을 때 기기 3대를 새로고침하면 "통신 실패" 토스트가 3번 뜹니다. 2초 안에 같은 문구가 또 오면 무시하게 만들어 봅니다.
  • 고칠 파일: DeviceViewModel.showToast(또는 작은 새 클래스)
  • 완료 기준: 같은 문구가 2초 안에 다시 오면 무시되고, 시간을 함수 인자로 받아 단위 테스트로 확인할 수 있습니다.
힌트마지막 문구와 시각을 기억해 두는 ToastThrottle.shouldShow(String message, long nowMillis)를 만들어 보세요. 시각을 인자로 받으면 테스트가 쉬워집니다.
정답 
final class ToastThrottle {
    private String last; private long lastAt;
    boolean shouldShow(String message, long now) {
        boolean same = message.equals(last) && now - lastAt < 2000;
        last = message; lastAt = now;
        return !same;
    }
}
