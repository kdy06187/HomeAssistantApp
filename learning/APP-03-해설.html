3코드 해설

조각 1 · 오류 문구를 한 곳에서 (#13) ErrorMessages

public static String fromJson(String body) {
    JsonElement root = new JsonParser().parse(body);
    if (!root.isJsonObject()) return null;
    String message = stringOrNull(obj, "message");          // {"result","message"} 모양
    return message != null ? message : stringOrNull(obj, "error");  // {"error"} 모양
}

public static String describe(Response<?> response) {
    String fromServer = fromJson(response.errorBody().string());
    return fromServer != null ? fromServer : "HTTP " + response.code();
}
왜 한 곳에? · 서버 오류 모양이 두 가지다(§6 I-03). v2.0에서 하나로 정리되면 이 파일만 고치면 된다. ViewModel 여섯 곳은 describe(response) 한 줄만 부른다.
왜 errorBody? · Retrofit은 2xx가 아니면 본문을 body()가 아니라 errorBody()에 담는다. 그리고 string()은 한 번만 읽을 수 있다(두 번째는 빈 값).
왜 null을 돌려주나? · HTML 오류 페이지처럼 JSON이 아니면 억지로 보여 주지 않고 "HTTP 500"으로 대신한다. 예외로 앱이 죽지 않게 RuntimeException을 잡는다.
빼면? · "삭제 실패: 서버 오류"만 보여서, 기기가 없는 건지 서버가 고장 난 건지 알 수 없다.

조각 4 · OFF 뒤 다시 확인 (#15) Handler.postDelayed

// 성공한 OFF 뒤
if (PowerOffRecheck.shouldRecheck(command, true)) scheduleRecheck(targetId);

private void scheduleRecheck(String deviceId) {
    cancelRecheck(deviceId);                       // 예전 예약이 있으면 버린다
    Runnable recheck = () -> syncDeviceState(deviceId, true);
    pendingRechecks.put(deviceId, recheck);
    mainHandler.postDelayed(recheck, PowerOffRecheck.DELAY_MS);   // 50초
}

@Override protected void onCleared() { mainHandler.removeCallbacksAndMessages(null); }
정한 값이유 (계약서에는 간격·횟수가 없다)
지연 50초서버가 전원을 끊는 45초 + 여유 5초. 더 일찍 물으면 아직 ON이다.
1번45초는 서버가 정한 고정 시간이다. 계속 물으면 서버와 기기에 부담만 준다.
성공한 OFF 전부E1에 드라이버 정보가 없어 PC 드라이버 기기를 구분할 수 없다. 드라이버가 없는 기기는 요청 한 번이 더 갈 뿐이다.
isManualRefresh=true서버 DB 값이 아니라 기기에 바로 물어보게 한다(계약서 E5).
왜 기기별 Map? · 50초 안에 사용자가 다시 켜면(ON) 예전 OFF 재확인은 의미가 없다. 기기 ID로 예약을 찾아 취소한다.
왜 onCleared? · ViewModel이 사라진 뒤에 예약이 실행되면 아무도 보지 않는 요청을 보낸다. 사라질 때 모두 지운다.
빼면? · PC를 끄면 화면은 계속 "ON"이다. 사용자가 직접 새로고침해야 OFF가 보인다.

4용어 풀이

errorBody
Retrofit에서 HTTP 코드가 2xx가 아닐 때 서버 본문이 들어가는 곳. 한 번만 읽을 수 있는 스트림이다.
누적값 / 구간 사용량
누적값은 계량기처럼 처음부터 지금까지의 합계, 구간 사용량은 두 시점 사이에 쓴 양(뒤 값 − 앞 값)이다.
Handler.postDelayed
정해진 시간 뒤에 메인 스레드에서 작업을 실행하도록 예약한다. removeCallbacks로 취소할 수 있다.
onCleared
ViewModel이 더는 쓰이지 않아 없어지기 직전에 불리는 메서드. 예약·구독 같은 뒷정리를 여기서 한다.

5이해도 질문

  1. 서버가 400에 {"result":"error"}만 주면 토스트에는 무엇이 나올까?
    정답 보기message도 error도 없어서 fromJson이 null을 돌려주고, describe는 "HTTP 400"으로 대신한다. 예: "삭제 실패: HTTP 400".
  2. 누적값이 [100, 200, 350]인데 정렬하지 않고 최신순 [350, 200, 100]을 그대로 intervalUsage에 넣으면?
    정답 보기차이가 −150, −100으로 모두 음수라 [0, 0]이 된다. 차트가 바닥에 붙는다. 그래서 정렬이 먼저다.
  3. OFF를 누르고 20초 뒤 ON을 누르면 50초 재확인은 어떻게 될까?
    정답 보기controlDevice가 시작할 때 cancelRecheck로 예전 예약을 지운다. ON은 재확인 대상이 아니라 새 예약도 없다.

실습 A · OFF가 될 때까지 최대 3번 재확인 조각 4 응용

목표50초 뒤 확인했는데 아직 ON이면, 20초 간격으로 최대 2번 더 확인한다(총 3번). OFF가 보이면 멈춘다. 고칠 파일viewmodel/PowerOffRecheck.java(규칙 추가), viewmodel/DeviceViewModel.java, 테스트 PowerOffRecheckTest.java 완료 기준① shouldRetry("ON", 1) true, shouldRetry("OFF", 1) false, shouldRetry("ON", 3) false ② 빌드와 기존 34개 테스트 통과
힌트
  • 판정은 순수 함수로: static boolean shouldRetry(String stateAfterCheck, int attemptsDone). 상수 MAX_ATTEMPTS = 3, RETRY_DELAY_MS = 20_000.
  • 지금 재확인은 syncDeviceState()를 그대로 부른다. 결과 상태를 받아야 하므로 콜백(Consumer<String>)을 받는 변형을 하나 만든다.
정답 보기 
// PowerOffRecheck
public static final int MAX_ATTEMPTS = 3;
public static final long RETRY_DELAY_MS = 20_000L;
/** 확인 결과가 아직 OFF가 아니고, 횟수가 남았으면 다시 확인한다. */
public static boolean shouldRetry(String stateAfterCheck, int attemptsDone) {
    return !"OFF".equals(stateAfterCheck) && attemptsDone < MAX_ATTEMPTS;
}

// DeviceViewModel
private void scheduleRecheck(String deviceId, int attemptsDone, long delayMs) {
    cancelRecheck(deviceId);
    Runnable recheck = () -> {
        pendingRechecks.remove(deviceId);
        syncDeviceState(deviceId, true, state -> {
            int done = attemptsDone + 1;
            if (PowerOffRecheck.shouldRetry(state, done)) {
                scheduleRecheck(deviceId, done, PowerOffRecheck.RETRY_DELAY_MS);
            }
        });
    };
    pendingRechecks.put(deviceId, recheck);
    mainHandler.postDelayed(recheck, delayMs);
}
// 처음 호출: scheduleRecheck(targetId, 0, PowerOffRecheck.DELAY_MS);

// 테스트
// 아직 ON이고 횟수가 남았으면 다시 확인한다
@Test
public void stillOn_retriesUntilLimit() {
    assertTrue(PowerOffRecheck.shouldRetry("ON", 1));
    assertFalse(PowerOffRecheck.shouldRetry("OFF", 1));
    assertFalse(PowerOffRecheck.shouldRetry("ON", 3));
}

실습 B · 차트 단위를 Wh로 조각 3 응용

목표구간 사용량이 mWh라 숫자가 크다(예: 150000). Y축과 라벨을 Wh로 바꿔 150.0처럼 보여 준다. 고칠 파일view/EnergyLogTimeline.java에 toWh(long mWh), view/EnergyLineChartView.java, 테스트 완료 기준① toWh(150000) == 150.0 ② toWh(0) == 0.0 ③ 데이터셋 이름이 "구간 사용량 (Wh)" ④ 테스트 통과
힌트
  • 1 Wh = 1000 mWh. 소수점이 필요하므로 / 1000.0(double)로 나눈다. / 1000(정수)이면 150999도 150이 된다.
  • 테스트에서 double 비교는 assertEquals(150.0, 값, 0.0001)처럼 허용 오차를 준다.
정답 보기 
// EnergyLogTimeline
/** 밀리와트시를 와트시로. 정수 나눗셈으로 소수점이 잘리지 않게 1000.0으로 나눈다. */
public static double toWh(long mWh) {
    return mWh / 1000.0;
}

// EnergyLineChartView
