v2.0 브랜치 · 계약 v2.0 초안 E4·E5·E6·E7 · 2026-11-24

1한눈에 보기

  • 삭제: v2.0의 삭제는 "숨김"이다. 90일 안에 다시 등록하면 기록을 이어받는다. 서버가 unpaired: false(기기 쪽 해제 실패)를 주면 대화상자로 "기기를 초기화해 주세요"를 띄운다. 404(이미 없음)는 실패가 아니라 "이미 삭제된 기기입니다" + 목록 새로고침(D7).
  • 404 = 기기가 사라짐: E5·E6·E7·E2가 DEVICE_NOT_FOUND를 주면 목록을 새로고침해 화면에서 지운다. 대시보드는 기기마다 요청을 보내므로 404가 몰려 올 수 있어, 0.5초 안의 404는 새로고침 1번으로 묶는다(RefreshGate).
  • 그대로인 것: E6 502·400은 지금처럼 요청 전 상태 + 실패 문구(불일치 #12 처리 유지).

3코드 해설

① 새로고침 묶기

private void scheduleListRefresh() {
    if (!listRefreshGate.tryClaim()) return;      // 이미 예약됨
    mainHandler.postDelayed(() -> {
        listRefreshGate.release();
        fetchDevices();
    }, LIST_REFRESH_DELAY_MS);                   // 500ms
}
무엇을 첫 404가 오면 0.5초 뒤 새로고침을 예약하고, 그 사이에 온 404는 버린다.
왜 대시보드는 기기 하나에 E6·E7을 동시에 보낸다. 사라진 기기가 둘이면 404가 4개다. 묶지 않으면 목록 요청이 4번 가고, 목록이 바뀔 때마다 대시보드가 다시 E6·E7을 보내 요청이 불어난다.
빼면 같은 목록 응답이 연달아 와 화면이 여러 번 다시 그려진다.

② 삭제 응답

Callback<ControlResponse>

ApiError error = ApiError.from(response);

else showFailure("삭제 실패: ", error);
왜 대화상자 토스트는 2초쯤 뒤 사라진다. "기기를 직접 초기화해야 한다"는 사용자가 할 일이므로, 확인을 누를 때까지 남겨 둔다.
왜 Boolean.FALSE.equals unpaired가 빠지거나 null이면 경고하지 않는다. 서버가 실패라고 분명히 말할 때만 경고해 잘못된 경고를 막는다.
왜 MainActivity에서 삭제 버튼은 Device 탭에 있지만, 응답이 오기 전에 탭을 바꿀 수 있다. 토스트처럼 액티비티가 관찰해야 어느 탭에서도 보인다.

4용어 풀이

  • 숨김 삭제(soft delete): 데이터를 바로 지우지 않고 "삭제됨" 표시만 하는 방식. 나중에 되살릴 수 있다.
  • unpair(페어링 해제): 기기와 서버의 연결 정보를 기기 쪽에서도 지우는 일.
  • 디바운스·묶기: 짧은 시간에 여러 번 일어난 일을 한 번만 처리하는 기법.
  • OneTimeEvent: 화면 회전 등으로 다시 관찰해도 한 번만 꺼내지는 값(APP-05에서 만든 것).

5이해도 질문

  1. 삭제 성공 뒤에는 fetchDevices()를 바로 부르고, 404 때는 scheduleListRefresh()를 쓰는 이유는?
  2. E5 404 때 토스트를 띄우지 않는 이유는?
  3. release()를 fetchDevices() 뒤가 아니라 앞에서 부르면 무엇이 달라질까?
정답 보기
  1. 삭제는 사용자가 한 번 누른 일이라 응답도 하나다. 404는 자동 조회 여러 개에서 한꺼번에 올 수 있어 묶어야 한다.
  2. E5는 재확인·새로고침 버튼 등에서 자주 불린다. 기기가 사라졌다는 것은 목록 새로고침으로 화면에서 보이므로 문구가 필요 없다.
  3. 거의 같다. 앞에서 풀면 fetchDevices() 응답을 기다리는 동안 온 새 404가 다시 예약될 수 있다(다음 목록이 최신이 되도록). 뒤에서 풀어도 fetchDevices()는 enqueue라 바로 돌아오므로 차이는 작다.

실습 1. 복구 기한 날짜 보여 주기

  • 고칠 파일: DeviceViewModel.java, 날짜 변환 순수 함수(06d의 EnergyLogTimeline 참고)
  • 완료 기준: "2027-02-15T03:00:00Z" → 서울 기준 "2027-02-15" 테스트 통과, 읽지 못하면 "90일 안에"로 대체.
힌트입력 패턴 yyyy-MM-dd'T'HH:mm:ss'Z'(UTC), 출력 패턴 yyyy-MM-dd(폰 시간대).
정답
static String localDate(String iso, TimeZone zone) {
    SimpleDateFormat in = new SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss'Z'", Locale.US);
    in.setTimeZone(TimeZone.getTimeZone("UTC"));
    SimpleDateFormat out = new SimpleDateFormat("yyyy-MM-dd", Locale.US);
    out.setTimeZone(zone);
    try { return out.format(in.parse(iso)); } catch (Exception e) { return null; }
}
