3코드 해설

① 분류는 순수 함수로

public static ControlOutcome of(int httpCode, ApiError error) {
    if (httpCode == 202) return ACCEPTED;
    if (httpCode >= 200 && httpCode < 300) return DONE;
    if (httpCode == 409) return BLOCKED;
    if (httpCode == 502) return UNREACHABLE;
    if (httpCode == 404 && error != null && error.is("DEVICE_NOT_FOUND")) return DEVICE_GONE;
    return FAILED;
}
무엇을 숫자와 문자열만 받아 결과 하나를 돌려준다. Android도 Retrofit도 필요 없다.
왜 ViewModel 콜백은 서버 없이 시험하기 어렵다. 판단을 떼어 내면 ControlOutcomeTest로 모든 경우를 몇 줄에 확인할 수 있다.
빼면 if-else가 콜백 안에 흩어져, 202를 200처럼 처리하는 실수를 테스트로 잡을 수 없다.

public static long delayMs(Integer delaySeconds) {

왜 +5초 서버가 전원을 끈 바로 그 순간에 물으면 기기가 아직 응답을 정리 중일 수 있다. 지금까지 쓰던 50초(45+5)와 같은 여유다(D5).
왜 대체값 계약상 202에는 항상 delaySeconds가 오지만, 빠졌을 때 0초로 바로 물으면 의미가 없다. 알려진 가장 긴 지연 45초를 쓴다.

③ errorBody는 한 번만

ApiError error = response.isSuccessful() ? null : ApiError.from(response);
ControlOutcome outcome = ControlOutcome.of(response.code(), error);
...

왜 분기에 쓸 code와 토스트에 쓸 message가 둘 다 필요하다. showFailure(prefix, response)를 또 부르면 본문이 비어 있어 서버 문구 대신 앱 폴백 문구가 뜬다.

4용어 풀이

  • 202 Accepted: "요청은 받았고 나중에 처리한다"는 HTTP 상태코드.
  • enum: 정해진 몇 가지 값만 가질 수 있는 Java 형식. switch와 잘 맞는다.
  • 순수 함수: 입력이 같으면 결과가 늘 같고, 바깥 상태를 바꾸지 않는 함수. 테스트하기 쉽다.
  • Handler.postDelayed: 메인 스레드에서 일정 시간 뒤 코드를 실행하도록 예약한다.

5이해도 질문

  1. 202를 받았을 때 화면에 바로 "OFF"를 보여 주지 않는 이유는?
  2. 경로가 틀려서 온 404(NOT_FOUND)를 DEVICE_GONE으로 보지 않는 이유는?
  3. 502 때 요청 전 상태(예: ON) 대신 OFFLINE을 보이면 무엇이 좋은가?
정답 보기
  1. 아직 실행 전이다. 45초 사이에 ON을 다시 누르면 서버가 대기 OFF를 취소하므로, 실제로 안 꺼질 수도 있다.
  2. 기기는 멀쩡히 있는데 목록을 새로고침하는 것은 낭비이고, 앱 버그(경로 오타)를 가린다.
  3. 서버가 이미 OFFLINE으로 기록했으므로, 다음 목록 조회 결과와 화면이 같아 깜빡임이 없다.

static boolean shouldRetry(String before, String now, int retriesLeft) {
    return retriesLeft > 0 && before != null && before.equals(now);
}
