1한눈에 보기

  • 문제: 토큰 칸에 줄바꿈이 섞인 값이 저장되면, 요청할 때마다 OkHttp가 Unexpected char 0x0a 예외를 던져 앱이 죽었다. 다시 켜도 같은 토큰을 읽어 또 죽었다(앱 데이터 삭제로만 복구).
  • 막는 곳 1 (입구): 설정 화면에서 저장하기 전에 앞뒤를 정리하고, 공백을 뺀 인쇄 가능한 ASCII만 받는다.
  • 막는 곳 2 (이미 저장된 값): AuthInterceptor가 헤더 예외를 잡아 서버에 보내지 않고 401을 직접 만든다. 그러면 기존 401 흐름이 "토큰을 다시 입력해 주세요" 안내와 설정 탭 이동을 해 준다.

2흐름 그림

OkHttp는 인터셉터를 추가한 순서대로 바깥→안쪽으로 지난다. 응답은 반대로 안쪽→바깥으로 돌아온다. 그래서 AuthInterceptor가 만든 401을 보려면 401 감시가 그보다 바깥(먼저 추가)에 있어야 한다.

3코드 해설

① 헤더 예외를 잡아 401로 바꾸기 (AuthInterceptor)

BEFORE
Request withAuth = original.newBuilder()
        .header("Authorization", "Bearer " + token)
        .build();   // 줄바꿈이면 여기서 예외 → 앱 종료
return chain.proceed(withAuth);
AFTER
try {
    withAuth = original.newBuilder()
            .header("Authorization", "Bearer " + token)
            .build();
} catch (IllegalArgumentException e) {
    return invalidTokenResponse(original); // 401
}
return chain.proceed(withAuth);
무엇을 OkHttp가 헤더 값 검사에서 던지는 IllegalArgumentException을 잡아, 서버에 보내지 않고 401 응답을 만들어 돌려준다.
왜 비동기(enqueue) 호출에서 인터셉터가 던진 RuntimeException은 OkHttp 작업 스레드에서 처리되지 않아 앱 전체가 죽는다. 401로 바꾸면 이미 있는 "토큰 틀림" 흐름을 그대로 탄다.
빼면 이미 잘못 저장된 토큰을 가진 사용자는 설정 화면에서 고치기도 전에 첫 요청(기기 목록)에서 죽는다.

② 입구에서 막기 (TokenFormat + SettingsFragment)

public static boolean isValid(String token) {
    if (token == null || token.isEmpty()) return false;
    for (int i = 0; i < token.length(); i++) {
        char c = token.charAt(i);
        if (c < 0x21 || c > 0x7E) return false;  // 공백·줄바꿈·한글 거절
    }
    return true;
}
무엇을 앞뒤는 trim()으로 정리하고, 가운데에 남은 공백·줄바꿈·한글은 거절한다.
왜 원래 코드도 trim()은 했지만 앞뒤만 지운다. 복사·붙여넣기로 가운데 들어간 줄바꿈은 남아서 크래시가 났다.
빼면 ①이 크래시는 막지만, 사용자는 저장은 "성공"인데 요청마다 401 안내만 보게 된다. 입력 순간에 알려 주는 편이 친절하다.

③ 인터셉터 순서 (RetrofitClient)

BEFORE
.addInterceptor(new AuthInterceptor(...))
.addInterceptor(new UnauthorizedInterceptor(...))
AFTER
.addInterceptor(new UnauthorizedInterceptor(...))
.addInterceptor(new AuthInterceptor(...))
왜 AuthInterceptor가 chain.proceed를 부르지 않고 응답을 바로 돌려주면, 그보다 안쪽 인터셉터는 실행되지 않는다. 401 감시를 바깥에 두어야 가짜 401도 본다. 서버가 준 진짜 401은 두 순서 모두에서 잘 보인다.

4용어 풀이

  • 인터셉터(Interceptor): OkHttp 요청·응답이 지나가는 길목에 끼워 넣는 코드. 헤더 추가, 응답 감시 등에 쓴다.
  • chain.proceed: "다음 인터셉터(또는 서버)로 넘긴다". 부르지 않으면 요청이 거기서 끝난다.
  • 인쇄 가능한 ASCII: 0x20(공백)~0x7E(~) 범위의 영문·숫자·기호. 여기서는 공백(0x20)도 뺐다.
  • 0x0a: 줄바꿈 문자(\n)의 코드 값. HTTP 헤더에 들어가면 헤더가 둘로 쪼개져 보안 문제가 되므로 OkHttp가 막는다.

5이해도 질문

  1. 원래 코드에도 trim()이 있었는데 왜 크래시가 났을까?
  2. 인터셉터 순서를 바꾸지 않았다면, 잘못된 토큰일 때 화면에는 무엇이 보였을까?
  3. 예외를 잡을 때 401 대신 IOException을 던졌다면 사용자에게 어떤 토스트가 떴을까?
정답 보기
  1. trim()은 앞뒤 공백만 지운다. 가운데 줄바꿈은 그대로 남는다.
  2. 아무것도 안 보였다. 401 감시가 실행되지 않아 토큰 안내·탭 이동이 없고, 요청별 실패 토스트는 401이면 생략하므로(ErrorMessages.isUnauthorized) 화면이 조용히 비어 있었다.
  3. onFailure로 가서 "서버 연결 실패: …"가 떴다. 서버 문제로 오해하게 된다.

실습 1. 토큰 최소 길이 안내

  • 목표: 서버 토큰은 32자 이상이다. 32자보다 짧으면 저장 전에 "토큰이 너무 짧습니다"를 띄운다.
  • 고칠 파일: TokenFormat.java(새 함수), SettingsFragment.java, TokenFormatTest.java
  • 완료 기준: 31자 거절·32자 통과 테스트가 통과한다.
힌트isValid와 따로 isLongEnough(String token)을 만들면 안내 문구를 다르게 줄 수 있다.
정답
public static final int MIN_LENGTH = 32;
public static boolean isLongEnough(String token) {
    return token != null && token.length() >= MIN_LENGTH;
}
// SettingsFragment: isValid 검사 다음에
if (!token.isEmpty() && !TokenFormat.isLongEnough(token)) { 토스트; return; }

실습 2. 인터셉터 순서 실험

  • 목표: AuthInterceptorTest.tokenWithNewline_returns401WithoutCrashingOrSending에서 두 인터셉터의 순서를 바꿔 보고, 어떤 단언이 깨지는지 확인한다.
  • 완료 기준: unauthorizedCalls가 0이 되어 실패하는 것을 보고, 이유를 한 줄로 설명한다.
