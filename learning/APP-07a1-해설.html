APP-07a-1 해설 — 색을 이름(토큰)으로 부르기

ui-1 브랜치 · UI 1차 07a(색 토큰·다크 모드) · 2026-11-24 · 화면 코드는 아직 안 바꿈(07a-2에서 교체)

1한눈에 보기

  • 전: 레이아웃·Java에 #F3F4F6, #333333 같은 색 값이 40곳 넘게 직접 적혀 있었다. 다크 모드를 켜도 이 색은 그대로라 어두운 배경에 어두운 글자가 나올 수 있다.
  • 후: 색에 역할 이름을 붙였다(color_surface, color_on_surface, state_on_bg …). 같은 이름을 values/colors.xml(라이트)과 values-night/colors.xml(다크)에 두면 Android가 폰 설정에 맞는 파일을 고른다.
  • 테마 연결: Material 3 위젯(스위치·버튼·하단 탭)은 colorPrimary, colorSurface 같은 테마 속성을 읽는다. themes.xml에서 이 속성을 토큰에 연결해, 직접 색을 주지 않은 위젯도 같은 색표를 쓴다.
  • 검사: 새 단위 테스트가 두 colors.xml을 읽어 ① 이름이 같은지 ② 글자/배경 15쌍의 대비가 4.5:1 이상인지 계산한다.

2흐름 그림 — 색 하나가 화면에 오기까지

3코드 해설

① 같은 이름, 다른 값

values/colors.xml (라이트)
<color name="state_on_bg">#FFC4EED0</color>
<color name="state_on_fg">#FF0D652D</color>
values-night/colors.xml (다크)
<color name="state_on_bg">#FF0F3D1E</color>
<color name="state_on_fg">#FFA8DAB5</color>
무엇을 켜짐 칩은 라이트에선 연한 초록 바탕 + 진한 초록 글자, 다크에선 반대로 진한 바탕 + 연한 글자다. 코드는 @color/state_on_bg 하나만 안다.
왜 색을 값이 아니라 역할로 부르면, 화면 코드를 건드리지 않고 색표만 바꿔 테마를 바꿀 수 있다.

② 다른 것은 작은 스타일 하나에만

<!-- values/themes.xml -->
<style name="Platform.Theme.HomeAssistantApp" parent="Theme.Material3.DayNight.NoActionBar">
    <item name="android:windowLightStatusBar">true</item>
</style>
<style name="Base.Theme.HomeAssistantApp" parent="Platform.Theme.HomeAssistantApp">
    <item name="colorSurface">@color/color_surface</item>
    <item name="colorOnSurface">@color/color_on_surface</item>
    …
</style>

<!-- values-night/themes.xml: Platform만 다시 정의 -->
<style name="Platform.Theme.HomeAssistantApp" parent="…">
    <item name="android:windowLightStatusBar">false</item>
</style>
왜 색 연결 30여 줄을 두 파일에 복사하면 한쪽만 고치는 실수가 생긴다. 라이트·다크가 정말 다른 것(상태 바 아이콘 밝기)만 Platform 스타일로 떼고, 연결은 values 한 곳에 둔다. 색 값 자체는 토큰이 알아서 바뀐다.
빼면(테마 연결 없이 토큰만) 직접 색을 안 준 스위치·FAB·하단 탭 표시기는 Material 3 기본 보라색으로 나와 우리 파란 강조색과 섞인다. 그래서 보조색(colorSecondary…)도 강조색에 맞췄다.

③ 대비를 숫자로 검사

static double contrast(int a, int b) {
    double la = luminance(a), lb = luminance(b);
    return (Math.max(la, lb) + 0.05) / (Math.min(la, lb) + 0.05);
}
무엇을 WCAG 공식이다. 색마다 사람이 느끼는 밝기(상대 휘도, 초록이 가장 큰 비중)를 구해 밝은 쪽/어두운 쪽 비율을 낸다. 검정/흰색이 21:1, 같은 색이 1:1.
왜 본문 글자는 4.5:1 이상이 읽기 쉬운 기준(AA)이다. 목업에서 고른 값이 기준을 넘는지 테스트가 지켜 주므로, 나중에 색을 바꿔도 바로 알 수 있다.
한계 실제 화면에는 겹침·투명도·글자 굵기가 섞인다. 화면에서의 대비는 Studio의 Accessibility Scanner로 따로 잰다.

4용어 풀이

  • 색 토큰: 색 값(#0B57D0) 대신 쓰는 역할 이름(color_primary).
  • 리소스 한정자: 폴더 이름 뒤의 -night 같은 꼬리표. 조건이 맞으면 그 폴더의 같은 이름 값을 먼저 쓴다.
  • 테마 속성(?attr/…): "지금 테마의 표면색"처럼 테마가 정하는 값. 위젯 라이브러리는 이것만 읽는다.
  • on-색: 그 색 위에 올라가는 글자·아이콘 색. color_on_primary는 파란 버튼 위 글자색.

  2. 왜 black·white는 이름 비교에서 빼 두었을까?

정답 보기
  1. 빌드는 되고 라이트 값(#444746, 짙은 회색)이 쓰여 어두운 칩 배경에 어두운 글자가 된다. 그래서 테스트로 막는다.
  2. 템플릿에서 온 색으로 어디서도 쓰지 않아 다크 짝이 필요 없다. 지우는 것은 승인 뒤에 한다.
  3. 상태 바 아이콘(시계·배터리)이 어둡게 그려져 어두운 배경에서 안 보인다.

6응용 실습

원본을 망가뜨리지 않게 새 브랜치에서 한다.

실습 1. "성공" 색쌍 추가

  • 목표: 등록 성공 화면용 color_success_container / color_on_success_container를 라이트(#C4EED0 / #0D652D)·다크(#0F3D1E / #A8DAB5)로 추가한다.
  • 고칠 파일: 두 colors.xml, ColorTokensTest의 TEXT_PAIRS
  • 완료 기준: 한쪽에만 넣으면 lightAndDark_haveSameTokenNames가 실패하고, 양쪽에 넣으면 통과한다.
힌트대비 검사에 넣으려면 {"color_on_success_container", "color_success_container"} 한 줄을 배열에 추가한다.

실습 2. 대비 실패 일부러 만들기

  • 목표: 라이트 state_unknown_fg를 #FFB08000(밝은 주황)으로 바꾸고 테스트를 돌려 본다.
  • 완료 기준: textPairs_meetContrastInLight가 실패 메시지에 실제 비율(약 2.7:1)을 보여 준다. 원래 값으로 되돌린다.
정답주황 글자를 주황 배경 위에 두면 밝기 차이가 작아서다. 그래서 "알 수 없음" 칩은 진한 갈색 글자(#5C4300)를 쓴다.
