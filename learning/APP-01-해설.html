3코드 해설

조각 1 · AuthInterceptor — 모든 요청에 헤더 붙이기

public Response intercept(Chain chain) throws IOException {
    Request original = chain.request();
    String token = tokenSupplier.get();          // 요청할 때마다 현재 토큰을 물어본다
    if (token == null || token.isEmpty()) {
        return chain.proceed(original);          // 토큰 없으면 그대로 → 서버가 401
    }
    Request withAuth = original.newBuilder()
            .header("Authorization", "Bearer " + token)
            .build();
    return chain.proceed(withAuth);
}
무엇을 하나 · 나가는 요청을 가로채 복사본에 Authorization 헤더를 넣고 다음 단계로 넘긴다.
왜 이렇게 · API 메서드 7개에 @Header를 하나씩 달면 빠뜨리기 쉽다. 인터셉터는 한 곳에서 모든 요청을 처리한다. 토큰 값 대신 Supplier를 받아서, 설정에서 토큰을 바꾸면 클라이언트를 다시 만들지 않아도 다음 요청부터 바로 적용된다.
빼면? · 서버가 모든 요청을 401로 거절한다. 기기 목록도 제어도 전혀 안 된다(수정 전 상태).

조각 3 · TokenStore.save — Keystore로 암호화

Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, getOrCreateKey()); // 키는 Keystore 안에서만 존재
byte[] iv = cipher.getIV();                          // 매번 새 IV
byte[] encrypted = cipher.doFinal(token.getBytes(UTF_8));
// 저장: "Base64(IV):Base64(암호문)"
무엇을 하나 · Keystore가 가진 AES 키로 토큰을 암호화하고, 복호화에 필요한 IV를 암호문 옆에 함께 저장한다.
왜 이렇게 · 키를 Keystore 밖으로 꺼낼 수 없으니, prefs 파일이 복사돼도(백업, 루팅 등) 토큰을 읽을 수 없다. GCM은 위변조 검사도 해 준다. EncryptedSharedPreferences는 지원이 중단됐고, Tink는 값 하나를 위해 넣기에는 너무 크다.
빼면(평문 저장)? · 백업이나 루팅된 기기에서 prefs XML을 열면 토큰이 그대로 보인다. 그 토큰이면 집 서버의 기기를 마음대로 켜고 끌 수 있다.

4용어 풀이

Bearer 토큰
"이 토큰을 가진 사람(bearer)을 믿어 달라"는 방식. 헤더에 Authorization: Bearer 값으로 보낸다.
401 Unauthorized
"누구인지 확인이 안 됐다"는 HTTP 응답. 토큰이 없거나 틀리면 온다.
인터셉터(Interceptor)
OkHttp에서 요청·응답을 중간에 가로채 바꾸거나 기록하는 부품. 여러 개를 줄줄이 연결할 수 있다.
Android Keystore
암호화 키를 앱 밖(보안 하드웨어나 OS 영역)에 보관하는 금고. 키를 쓸 수는 있지만 꺼낼 수는 없다.
AES-GCM / IV
AES 암호화의 한 방식. 내용을 숨기고 위변조도 검사한다. IV는 매번 바뀌는 시작값으로, 비밀은 아니지만 복호화할 때 필요하다.
volatile
여러 스레드가 같은 변수를 볼 때, 한쪽에서 바꾼 값이 다른 쪽에 바로 보이게 하는 자바 키워드.

5이해도 질문

  1. 설정 화면에서 토큰을 바꿨을 때, RetrofitClient.rebuildClient()를 다시 부르지 않아도 새 토큰이 쓰이는 이유는?
    정답 보기인터셉터가 토큰 값이 아니라 () -> apiToken(Supplier)을 받아서, 요청할 때마다 현재 값을 읽기 때문이다. setApiToken()으로 변수만 바꾸면 된다.
  2. 다른 휴대폰으로 앱 백업을 복원하면 토큰은 어떻게 될까? 앱은 그때 어떻게 동작할까?
    정답 보기암호문은 복원되지만 Keystore 키는 원래 기기에만 있어서 복호화가 실패한다. TokenStore.load()가 null을 돌려주고, 앱은 "토큰 없음"으로 보고 설정 탭을 연다.
  3. E7 수정에서 hasError() 검사만 넣고 DashboardAdapter는 그대로 뒀다면 충분했을까?
    정답 보기E7 경로는 막히지만, 다른 경로(앞으로 추가될 API나 서버 버그)로 상태가 null이 되면 다시 크래시가 난다. 원인(데이터)과 증상(화면)을 둘 다 막는 것이 안전하다.

실습 A · X-App-Version 헤더를 붙이는 인터셉터 추가하기 조각 1 응용

목표모든 요청에 X-App-Version: 1.0(앱 versionName)을 붙인다. 서버가 나중에 앱 버전별로 다르게 응답할 때 쓸 수 있다. 고칠 파일network/AppVersionInterceptor.java(새로 만듦), network/RetrofitClient.java, 테스트 network/AppVersionInterceptorTest.java 완료 기준① 빌드 성공 ② 테스트에서 헤더 값이 "1.0"이다 ③ 기존 AuthInterceptorTest 3개도 계속 통과한다
힌트
  • AuthInterceptor를 그대로 본떠 만든다. 버전 문자열은 생성자로 받는다(테스트하기 쉬움).
  • 앱에서는 BuildConfig.VERSION_NAME을 쓰면 된다. AGP 8에서는 buildFeatures { buildConfig = true }가 필요하다.
  • 테스트는 AuthInterceptorTest의 "가짜 응답을 돌려주는 마지막 인터셉터" 방식을 그대로 쓴다.
정답 보기 
public class AppVersionInterceptor implements Interceptor {
    private final String version;
    public AppVersionInterceptor(String version) { this.version = version; }

    @Override
    public Response intercept(Chain chain) throws IOException {
        Request req = chain.request().newBuilder()
                .header("X-App-Version", version)
                .build();
        return chain.proceed(req);
    }
}

// RetrofitClient.rebuildClient()
.addInterceptor(new AuthInterceptor(() -> apiToken))
.addInterceptor(new AppVersionInterceptor(BuildConfig.VERSION_NAME))

// 테스트
// 버전 헤더가 붙는다
@Test
public void versionGiven_addsAppVersionHeader() throws Exception {
    // AuthInterceptorTest.send()와 같은 방식으로 captured 요청을 얻은 뒤
    assertEquals("1.0", captured.get().header("X-App-Version"));
}

실습 B · E6 오류 응답에서도 상태를 덮어쓰지 않게 (불일치 #12) 조각 4 응용

목표E6(현재 전력)이 400 + {"error": "..."}로 오면, 지금은 기기를 OFFLINE으로 바꾼다. 이 대신 원래 상태를 유지하고 서버의 error 메시지를 토스트로 보여 준다. 고칠 파일viewmodel/DeviceViewModel.java의 fetchDeviceEnergy(), 필요하면 dto/EnergyResponse.java 완료 기준① 400 응답 뒤에도 기기 상태가 요청 전과 같다 ② 토스트에 서버 메시지("등록되지 않은 기기입니다." 등)가 나온다 ③ 빌드와 기존 테스트 통과
힌트
  • E7과 다른 점: E6은 오류일 때 HTTP 400이다. 그래서 오류 본문이 response.body()가 아니라 response.errorBody()에 있다.
  • new Gson().fromJson(response.errorBody().charStream(), EnergyResponse.class)처럼 읽으면 된다. EnergyResponse에 @SerializedName("error") public String error;를 추가한다.
  • 요청 전에 findState(deviceId)로 이전 상태를 기억해 두는 방법은 E7과 같다.
정답 보기 
public void fetchDeviceEnergy(String deviceId) {
    final String previousState = findState(deviceId);
    updateDevice(deviceId, d -> d.setState("LOADING"));
    RetrofitClient.getApi().getDeviceEnergy(deviceId).enqueue(new Callback<EnergyResponse>() {
        @Override
        public void onResponse(Call<EnergyResponse> call, Response<EnergyResponse> response) {
            if (response.isSuccessful() && response.body() != null) {
                // ... 기존 성공 처리 그대로 ...
            } else {
                String message = "전력 조회 실패: " + response.code();
                try {
                    EnergyResponse err = new Gson().fromJson(
                            response.errorBody().charStream(), EnergyResponse.class);
                    if (err != null && err.error != null) message = "전력 조회 실패: " + err.error;
                } catch (Exception ignored) { /* 본문이 JSON이 아니면 코드만 보여 준다 */ }
                updateDevice(deviceId, d -> d.setState(previousState)); // OFFLINE으로 바꾸지 않는다
                toastMessage.setValue(message);
            }
        }
        @Override
        public void onFailure(Call<EnergyResponse> call, Throwable t) {
            updateDevice(deviceId, d -> d.setState(previousState));
            toastMessage.setValue("통신 실패: " + t.getMessage());
        }
    });
}

참고: onFailure에서도 원래 상태로 되돌리면 불일치 #11(LOADING이 풀리지 않음)의 E6 부분까지 함께 고쳐진다.
