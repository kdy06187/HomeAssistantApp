ui-1 브랜치 · 에뮬레이터 확인 문제 E1·E3 · 2026-11-26

1한눈에 보기

  • E1 여백: targetSdk 35 앱은 Android 15에서 화면이 상태 표시줄·제스처 바 아래까지 그려진다(edge-to-edge). MainActivity 한 곳에서 여백을 나눠 준다: 위·좌우 → 루트, 아래 → 하단 탭이 보이면 탭이 스스로, 숨으면 Fragment 자리. 키보드(IME)도 같은 계산에 넣었다. 낮은 버전도 EdgeToEdge.enable로 같게 맞췄다.
  • E3 실패 화면: 목록을 한 번도 받지 못했는데 요청이 실패하면 홈·기기 탭 가운데에 "목록을 불러오지 못했어요 + 다시 시도". 0개를 받은 "아직 등록된 기기가 없어요"와 나눈다(ListScreenState).

2흐름 그림 — 여백을 누가 갖나

3코드 해설

① 한 곳에서 나누고, 쓴 만큼 빼서 넘기기

Insets bars = insets.getInsets(systemBars() | displayCutout());
v.setPadding(bars.left, bars.top, bars.right, 0);
applyBottomInset();
return insets.inset(bars.left, bars.top, bars.right, 0);
왜 한 곳 화면마다(설정·상세·QR…) 따로 처리하면 빠뜨리기 쉽고, 배너는 어느 화면 위에도 뜬다. 모든 화면이 루트 안에 있으니 루트 한 번이면 된다.
왜 inset(...)으로 빼서 넘기나 하단 탭도 여백을 스스로 처리한다. 위·좌우를 그대로 넘기면 탭이 좌우 여백을 한 번 더 넣는다.
빼면 배너 글자가 시계와 겹치고, 전체 화면 아래 버튼이 제스처 바에 눌린다(에뮬레이터 확인 E1).

② 아래 여백 계산은 순수 함수로

if (bottomNavShown) return Math.max(0, imeBottom - bottomNavHeight);
return Math.max(systemBarsBottom, imeBottom);
왜 키보드는 하단 탭을 덮으며 올라온다. 탭이 보이면 탭 높이만큼은 이미 비어 있으니 그 차이만 더 비운다. Android 없이 시험할 수 있게 계산만 떼어 냈다(BottomInsetTest).

③ "0개"와 "못 받음" 나누기

if (devices == null) return lastLoadFailed ? LOAD_FAILED : LOADING;
return devices.isEmpty() ? EMPTY : CONTENT;
왜 null로 나누나 목록 LiveData는 첫 응답 전까지 null이다. 한 번이라도 받았으면(0개 포함) 새로고침이 실패해도 마지막 목록을 두고 배너만 알린다. 그래야 잠깐 끊겼다고 기기들이 사라지지 않는다.

4용어 풀이

  • edge-to-edge: 앱 화면이 상태 표시줄·내비게이션 바 뒤까지 그려지는 방식. 앱이 여백(insets)을 직접 비워야 한다.
  • WindowInsets: 시스템이 "이만큼은 가려져 있다"고 알려 주는 값(위·아래·좌우).
  • IME: 화면 키보드. 올라오면 아래 여백으로 높이를 알려 준다.
  • adjustResize: 키보드가 뜰 때 화면을 밀지 말고 여백으로 처리하라는 설정.

  2. 기기 10개를 받은 뒤 서버가 꺼지고 당겨서 새로고침하면 기기 탭은?

6응용 실습

목표: 하단 탭이 숨은 전체 화면에서 Fragment 바탕색이 제스처 바 뒤까지 이어지게 하기(지금은 루트 바탕색이 보임). 고칠 곳: 새 브랜치에서 applyBottomInset. 완료 기준: 패딩 대신 각 화면 맨 아래 버튼 영역에만 여백이 들어가고 바탕은 끝까지 그려짐.

힌트fragmentContainer에 clipToPadding=false를 주거나, 여백 값을 Fragment에 넘겨 스크롤 뷰의 paddingBottom에만 더한다.
정답 방향Fragment가 ViewCompat.setOnApplyWindowInsetsListener로 자기 스크롤 뷰에 아래 여백을 넣고, 루트는 아래를 건드리지 않는다. 대신 화면마다 처리해야 해서 이번에는 한 곳 방식을 골랐다.
