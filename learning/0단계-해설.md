# 0단계 해설 — 이 앱은 이렇게 돌아간다

대상: HomeAssistantApp (기준 커밋 `0ca5dbf`). 경로 접두사 `app/src/main/java/com/example/homeassistantapp/`는 생략합니다.
자세한 근거는 `analysis/as-is-설계.md`, `analysis/문제점.md`에 있습니다. 여기서는 큰 그림만 잡습니다.

## 1. 큰 그림 한 장

```
[화면 Fragment] -> [ViewModel] -> [RetrofitClient/Api] -> (HTTP) -> [스마트홈 서버] -> 기기
      ^                |
      +-- LiveData ----+        (SharedPreferences: 서버 주소, Wi-Fi, 대시보드 순서를 기억)
```

이 앱은 기기와 직접 통신하지 않습니다. 서버에 "이 기기 켜줘"라고 부탁하는 리모컨입니다. 그래서 앱 코드의 일은 두 가지입니다.
1. 서버에서 받은 정보를 화면에 그린다.
2. 사용자의 조작을 서버에 전달한다.

## 2. 부분별 역할 (쉬운 말 풀이)

| 용어 | 뜻 | 이 앱에서 |
|---|---|---|
| Fragment | 화면 한 장 | `HomeFragment`(대시보드), `DeviceFragment`(기기 관리), `SettingsFragment`(설정). `MainActivity`가 하단 탭에 따라 갈아 끼움 |
| ViewModel | 화면 뒤에서 데이터와 서버 호출을 맡는 담당자 | `viewmodel/DeviceViewModel.java` 하나가 서버 호출을 전부 처리 |
| Retrofit | 인터페이스만 적으면 HTTP 요청 코드를 만들어 주는 도구 | `api/HomeAssistantApi.java`(주문서), `network/RetrofitClient.java`(서버 주소를 쥔 창구) |
| enqueue | "요청 보내 놓고 기다리지 말고, 답이 오면 알려줘" | 모든 서버 호출이 이 방식. 답이 오면 `onResponse`(받음) 또는 `onFailure`(통신 자체 실패)가 실행됨 |
| LiveData | "값이 바뀌면 구경꾼에게 알려주는 상자" | ViewModel이 값을 넣으면, 지켜보던 화면이 자동으로 다시 그림 |
| SharedPreferences | 앱 안의 작은 메모장(키-값). 앱을 꺼도 남음 | 서버 IP/포트, Wi-Fi 정보, 대시보드 정렬 순서 |

### LiveData: 화면을 "직접 고치지 않는" 이유
`viewmodel/DeviceViewModel.java:30`에 `MutableLiveData<List<Device>> deviceList`가 있습니다. ViewModel은 이 상자에 값을 넣기만 합니다(`:44` `deviceList.setValue(...)`). 화면은 `observe`로 상자를 지켜보다가 값이 바뀌면 스스로 다시 그립니다. 서버 담당(ViewModel)과 그리기 담당(Fragment)이 서로를 몰라도 되게 하는 장치입니다.
밖에는 읽기 전용 `LiveData`만 보여 주고(`:35`) 안에서만 `MutableLiveData`로 씁니다. 아무 화면이나 값을 마음대로 바꾸지 못하게 하려는 습관입니다.

### SharedPreferences: 앱이 "기억하는 것" 2곳
- `HomeAssistantPrefs`: `SERVER_IP`, `SERVER_PORT`, `WIFI_SSID`, `WIFI_PASSWORD`. 설정 화면이 쓰고(`fragment/SettingsFragment.java:67-70`), 앱 시작 때 `MainActivity.java:23-28`이 읽어 Retrofit을 준비합니다.
- `DashboardPrefs`: `device_order`, `<기기id>_widget_order`. 대시보드에서 드래그한 순서를 쉼표 문자열로 저장합니다.
- 기억하는 건 이 둘뿐이고 DB는 없습니다. 기기 목록 자체는 켤 때마다 서버에서 새로 받아 옵니다.

## 3. 요청 하나가 지나가는 길: 대시보드 스위치 켜기

1. 사용자가 스위치를 누릅니다. `view/widgets/ToggleViewHolder.java:51-56`이 `onToggle(deviceId, isChecked)`를 부릅니다.
2. `fragment/HomeFragment.java:46-49`가 "ON"/"OFF" 글자를 정해 `viewModel.controlDevice(deviceId, command)`를 호출합니다. Fragment는 서버 주소도 HTTP도 모르고 ViewModel에 부탁만 합니다.
3. `viewmodel/DeviceViewModel.java:60`: 먼저 그 기기의 `state`를 `"LOADING"`으로 바꿉니다. 이어서 `updateDevice`(`:237-250`)가 같은 목록을 다시 `setValue`해 화면에 "처리 중"을 보여 줍니다.
4. `:63`: `RetrofitClient.getApi().controlDevice(request).enqueue(...)`가 `POST /api/control`을 서버로 보냅니다.
5. 답이 오면 `onResponse`(`:65-73`)가 실행됩니다. 성공이면 서버가 준 `status`로 `state`를 덮어씁니다(`:68`). 실패 응답이면 `"OFFLINE"`으로 바꿉니다(`:70`).
6. `state`가 바뀔 때마다 LiveData가 다시 방출되고, `view/DashboardAdapter.java`가 `state`를 보고 "연결됨/오프라인/로딩" 표시를 정합니다(`:96-113`).

핵심: 화면은 `Device.state`라는 문자열 하나를 보고 모양을 정합니다. 그래서 이 문자열이 잘못 남으면 화면도 잘못 남습니다.

## 4. 대표 문제점 P-04: LOADING 고착 (코드로 따라가기)

### 무슨 일이 생기나
요청을 보내기 직전에 `state = "LOADING"`을 넣습니다. 그런데 요청이 실패하는 길에서 이 값을 되돌리지 않습니다. 그러면 기기가 영원히 "로딩 중"에 머뭅니다.

### 코드로 보기
`controlDevice`의 두 갈래를 비교해 봅니다.

| 갈래 | 위치 | LOADING을 치우는가 |
|---|---|---|
| 서버가 정상 응답 | `:66-68` | 예 (`status`로 덮어씀) |
| 서버가 오류 응답 | `:69-72` | 예 (`"OFFLINE"`으로 바꿈) |
| 통신 자체 실패(서버 꺼짐, 타임아웃) | `:75-78` `onFailure` | **아니오. 토스트만 띄움** |

같은 문제가 더 있습니다. `syncDeviceState`(`:156-175`)는 `if (response.isSuccessful() ...)`(`:161`)만 있고 `else`가 없어서, 서버가 500 같은 오류를 주면 `LOADING`이 그대로 남습니다. `onFailure`(`:170-173`)는 `"OFFLINE"`으로 바꾸므로 괜찮습니다. 이렇게 같은 파일 안에서도 처리가 들쭉날쭉합니다.

### 화면에서 어떻게 보이나
`view/DashboardAdapter.java:96-100`: `LOADING`이면 진행 바를 보이고 새로고침 버튼을 끕니다(`setEnabled(false)`, "중복 클릭 방지"). 그래서 서버가 꺼진 채 스위치를 누르면 그 섹션은 새로고침 버튼도 못 누르는 상태로 남습니다. 타임아웃도 60초(`network/RetrofitClient.java:24-26`)라 실패 판정까지 오래 걸립니다. 기기 관리 탭에서 목록을 다시 받아야 풀립니다.

### 왜 이런 일이 생겼을까 (설계 관점)
- "시작할 때 LOADING, 끝날 때 결과"는 좋은 생각입니다. 하지만 "끝"이 성공, 서버 오류, 통신 실패 3가지인데 한 갈래를 놓쳤습니다.
- `state` 한 필드가 "전원 ON/OFF", "연결 OFFLINE", "요청 진행 LOADING"을 모두 맡습니다(문제점 P-05). 그래서 LOADING 하나를 놓쳐도 전원 상태까지 같이 사라집니다.
- 고치는 방향 후보: (a) 모든 `onFailure`/else에서 되돌리기, (b) 진행 상태를 `state`와 별도 필드(`isLoading`)로 분리. (a)는 쉽고 (b)는 구조가 좋아집니다. 이 선택은 1단계 기획에서 사용자와 정합니다.

## 5. 이 구조에서 눈여겨볼 점 (추가 읽을거리)
- Fragment는 탭을 누를 때마다 새로 만들어지지만(`MainActivity.java:36-48`), `DeviceViewModel`은 `requireActivity()`로 공유해서 기기 목록이 살아남습니다. 대시보드와 기기 관리가 같은 데이터를 보는 이유입니다.
- 상태 하나가 바뀔 때마다 목록 전체를 다시 방출합니다(`:245`). 간단하지만 화면이 자주 다시 그려집니다(P-10).
- 서버 주소 기본값이 파일마다 다릅니다(P-07). 같은 값을 여러 곳에 적으면 어긋난다는 좋은 반면교사입니다.
