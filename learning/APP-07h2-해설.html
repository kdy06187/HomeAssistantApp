1한눈에 보기

  • 상태 하나(U27·U19): RetrofitClient에 흩어져 있던 "연결 상태 · 안내 대기 플래그 · 401 신호"를 ConnectionState 하나로 합쳤다. 상태를 바꾸는 함수가 "토큰 오류로 막 들어갔다"(ENTERED_TOKEN_ERROR)를 같은 잠금 안에서 돌려주고, 1회 안내 플래그도 그 안에서 함께 바뀐다.
  • 세대 번호(U18): 설정을 저장해 클라이언트를 다시 만들면 번호가 오른다. 옛 클라이언트의 늦은 401·실패는 번호가 달라 무시된다.
  • 화면(U2·U3): 설정 화면은 연결 상태를 관찰해 이 탭에 있는 동안 401이 와도 토큰 칸에 오류를 띄운다. 배너의 "설정으로" 버튼은 설정 탭 위에 전체 화면이 열려 있으면 보이고, 누르면 그 화면을 닫는다.
  • 등록 확인 중 401(U21): 폴링을 "확인 불가"로 끝내지 않고 멈춘다(PAUSED). 진행 화면은 그대로, 토큰을 저장하면 같은 작업을 이어서 묻는다.
  • 중복 LiveData 없앰(U31): commissioning(참/거짓)을 지우고 버튼 글자는 commissionStatus.isActive()로 정한다.

2흐름 그림 — 401 하나가 지나가는 길

3코드 해설

① 확인과 설정을 한 잠금 안에서

before (RetrofitClient)
if (!connection.onResponse(code)) return;
publishLatest();
if (connection.get() == TOKEN_ERROR) {
    unauthorizedPending.set(true);
    unauthorizedSignal.postValue(true);
}
after (ConnectionState)
private Change set(Kind next) {
    if (next == kind) return Change.NONE;
    boolean entered = next == Kind.TOKEN_ERROR;
    kind = next;
    tokenNoticePending = entered;
    return entered ? ENTERED_TOKEN_ERROR : CHANGED;
}
무엇을 상태 변경과 "안내할 것이 있다" 표시를 synchronized 메서드 하나 안에서 같이 바꾼다.
왜 before는 상태를 바꾼 뒤 잠금 밖에서 get()을 다시 읽었다. 그 사이 다른 스레드나 설정 저장이 끼어들면 안내가 두 번 나가거나, 저장 직후 이미 풀린 오류로 설정 탭에 끌려갈 수 있었다.
빼면 토큰 오류가 풀린 뒤에도 플래그가 남아 엉뚱한 때 안내가 뜬다(after는 풀리면 플래그도 내린다).

② 세대 번호

.addInterceptor(new ConnectionStateInterceptor(listenerFor(connection.nextGeneration())))

public synchronized Change onResponse(int fromGeneration, int httpCode) {
    if (fromGeneration != generation) return Change.NONE;
    ...
왜 저장 전 틀린 토큰으로 보낸 요청이 저장 뒤에 401로 돌아오면, 새 토큰이 맞아도 배너가 다시 "토큰 오류"가 됐다. 감시자가 자기 번호를 들고 있으면 옛 클라이언트 결과를 걸러 낼 수 있다.
대안 옛 클라이언트의 요청을 모두 취소(dispatcher().cancelAll())할 수도 있지만, 진행 중인 등록 확인까지 끊긴다. 번호 비교가 더 좁고 안전하다.

③ 등록 확인 중 401은 "멈춤"

if (httpCode == 401) return Next.PAUSED;   // 결과 없이 멈춤
...
case PAUSED:
    pollRunnable = null;
    pausedJobId = jobId;                    // 저장 뒤 resumeCommissionPolling()
왜 예전엔 401을 "작업 없어짐"으로 보고 목록을 다시 받았다(또 401) → "확인 불가" 결과까지 떴다. 실제로 등록은 서버에서 계속 진행 중일 수 있다. 토큰만 고치면 같은 작업 ID로 결과를 알 수 있다.

4용어 풀이

  • 원자적(atomic): 여러 단계를 다른 스레드가 끼어들 수 없게 한 번에 하는 것.
  • 세대 번호(generation): 무언가를 새로 만들 때마다 올리는 번호. 옛것이 보낸 소식을 알아보는 데 쓴다.
  • LiveData 재전달: 화면 회전으로 관찰자가 다시 붙으면 마지막 값을 또 준다. 그래서 "1번만" 할 일은 따로 플래그로 관리한다.
  • 백스택(back stack): 뒤로 가기로 닫을 화면 쌓음. 0개면 탭 화면이 맨 위에 보인다.

  2. 설정 탭 위에 기기 상세가 열려 있다. 배너 "설정으로"를 누르면 왜 setSelectedItemId가 아니라 백스택을 비울까?
  3. 401 다음 곧바로 200이 와서 메인 스레드에는 OK만 전달됐다. 안내는?
정답 보기
  1. 안 뜬다. consumeTokenNotice()가 처음 한 번만 true.
  2. 이미 선택된 탭을 다시 선택하면 선택 콜백이 오지 않아 아무 일도 안 일어난다. 위의 전체 화면만 닫으면 설정이 보인다.
  3. 없다. 200으로 풀릴 때 플래그도 내려간다(tokenNoticePending = false).

6응용 실습

목표: "닿지 않음"에 들어간 순간에도 1번만 진동을 주고 싶다. 고칠 파일: ConnectionState(새 브랜치나 learning/exercise-connection/ 사본에서). 완료 기준: Change.ENTERED_UNREACHABLE을 더하고, 실패가 두 번 와도 한 번만 그 값을 돌려주는 테스트 통과.

힌트set()에서 next == Kind.UNREACHABLE인지 보고 돌려줄 값을 고른다. 같은 상태면 이미 NONE이 나간다.
정답
if (next == Kind.TOKEN_ERROR) return Change.ENTERED_TOKEN_ERROR;
if (next == Kind.UNREACHABLE) return Change.ENTERED_UNREACHABLE;
return Change.CHANGED;
