APP-06e 해설 — 기기 등록을 "접수 → 2초마다 확인"으로

v2.0 브랜치 · 계약 v2.0 초안 E3·E8 + 서버 13번 K 메모 · 2026-11-24 · 서버 13b 전 초안 기준

1한눈에 보기

  • 전: 등록 요청 하나가 페어링이 끝날 때까지(최대 2분 이상) 응답을 붙잡고 있었다. 그래서 이 경로만 읽기 타임아웃을 150초로 늘렸고, 타임아웃이 나면 결과를 알 수 없었다.
  • 후: 서버는 바로 202 + jobId로 접수만 알린다. 앱은 2초마다 GET /api/commission/{jobId}로 상태를 묻고, 성공·실패가 나오면 멈춘다. 210초가 지나면 멈추고 기기 목록으로 결과를 확인한다.
  • 보내기 전 검사: 이름 1~64자, Matter 수동 코드 11/21자리(-·공백은 앱이 지움), QR MT:…, TCP_DIY는 IPv4 또는 빈 값(빈 값이면 서버가 앱이 접속한 주소를 씀), SSID 32바이트·비밀번호 63바이트, 제어 문자 금지. Wi-Fi 값은 공백·따옴표를 허용하므로 trim을 없앴다.

3코드 해설

① 결정은 순수 함수, 예약은 ViewModel

static Next afterResponse(long elapsedMs, int httpCode, CommissionJobResponse body) {
    if (httpCode >= 200 && httpCode < 300 && body != null) {
        if (SUCCEEDED.equals(body.state)) return Next.SUCCEEDED;
        if (FAILED.equals(body.state)) return Next.FAILED;
    }
    if (httpCode == 404 || httpCode == 401) return Next.LOST;
    return elapsedMs + INTERVAL_MS > LIMIT_MS ? Next.TIMED_OUT : Next.POLL_AGAIN;
}
무엇을 "지난 시간 + 응답"만 보고 다음 할 일을 고른다. 끝 상태(성공·실패)는 상한을 넘었어도 그대로 받아들인다.
왜 2초 예약·네트워크는 단위 테스트가 어렵다. 결정만 떼어 내면 210초 경계(208.001초면 다음 폴링이 210초를 넘으므로 TIMED_OUT)를 숫자로 시험할 수 있다.
빼면(상한 없이) 서버가 작업을 잃어버린 채 PENDING만 주면 앱이 영원히 묻는다.

② 목록을 새로 받아도 임시 항목을 지키기

private List<Device> withPairingItem(List<Device> devices) {
    List<Device> result = devices == null ? new ArrayList<>() : new ArrayList<>(devices);
    if (pairingDevice != null && !result.contains(pairingDevice)) result.add(0, pairingDevice);
    return result;
}
// fetchDevices 성공 때
deviceList.setValue(withPairingItem(devices));
왜 예전엔 등록 요청 하나가 끝날 때까지 다른 목록 새로고침이 거의 없었다. 이제 등록이 최대 3분 넘게 걸리고, 그동안 당겨서 새로고침이나 404 새로고침이 일어나면 임시 "등록 중" 항목이 사라져 버린다.
빼면 등록이 진행 중인데 화면에서는 아무 표시가 없고, 추가 버튼만 잠긴 이상한 상태가 된다.

③ 입력 검사: 수동 코드 정리

BEFORE
String payload = editPayload.getText().toString();

왜 서버는 규칙을 어기면 400 한 가지로만 답한다. 앱이 먼저 "몇 자리인지"까지 알려 주면 사용자가 바로 고칠 수 있다.
주의 서버 13b가 끝나면 규칙이 바뀔 수 있다. 검사기는 한 파일에 모아 두어 그때 한 곳만 고친다.

4용어 풀이

  • 비동기 작업(job): 요청을 받은 즉시 "접수 번호"만 돌려주고, 실제 일은 뒤에서 하는 방식.
  • 폴링(polling): 결과가 나올 때까지 일정 간격으로 "끝났어?"라고 계속 묻는 것.
  • SystemClock.elapsedRealtime(): 폰이 켜진 뒤 흐른 시간. 사용자가 시계를 바꿔도 흔들리지 않아 경과 시간 계산에 쓴다.
  • UTF-8 바이트: 영문은 1바이트, 한글은 3바이트. Wi-Fi 이름 32바이트 제한은 글자 수가 아니라 바이트 수다.
  • 제어 문자: 줄바꿈·탭·널(\0)처럼 화면에 보이지 않는 문자.

정답 보기
  1. 탭을 바꾸면 계속된다. DeviceViewModel이 액티비티 범위이기 때문이다. 앱을 끄면 멈추고, jobId를 저장하지 않으므로(D8) 다시 켠 뒤 목록에서 결과를 본다.
  2. 서버 쪽 일시 오류일 수 있고 등록 작업 자체는 계속 진행 중일 수 있다. 상한(210초) 전까지는 다시 묻는다.
  3. 10자 × 3바이트 = 30바이트로 통과한다. 11자면 33바이트라 거절된다.

  • 완료 기준: 상태 문자열 → 표시 문구 순수 함수의 단위 테스트가 통과한다.
힌트Device에 새 필드를 만들기보다 powerInfo처럼 화면용 필드를 하나 두고, 변환은 static String pairingLabel(String state)로.
정답
static String pairingLabel(String state) {
    if ("PENDING".equals(state)) return "대기 중";
    if ("RUNNING".equals(state)) return "등록 중";
    return "등록 중";
}
