1한눈에 보기

  • 무엇을: 서버 v2.0의 실패 본문 {"error":{"code","message"}}를 읽는 ApiError를 만들고, 응답 DTO의 키 이름을 v2.0(lowerCamelCase)으로 바꿨다.
  • 왜: v1.0은 실패도 200으로 주는 곳이 있어 message == "명령 성공!" 같은 문자열로 성공을 판단했다. v2.0은 HTTP 상태코드만으로 성공을 판단하고, 결과 키(result·status·message)를 없앴다.
  • 함께: 키를 하나라도 놓치면 Gson이 조용히 null을 넣는다. 그래서 키를 고정하는 테스트(DtoKeysTest)를 두고, getType() 비교를 null에 안전한 꼴로 바꿨다.

2흐름 그림

06a에서는 code 분기를 아직 쓰지 않는다(06b·06c에서 404 → 목록 새로고침, 502 → OFFLINE 등). 지금은 문구만 쓴다.

3코드 해설

① 제어 성공 판정

BEFORE (v1.0)
if (response.isSuccessful() && body != null
        && body.isCommandSucceeded()) {   // message == "명령 성공!"
    ...
} else if (response.isSuccessful() && body != null) {
    // 200인데 실패
} else { ... }
AFTER (v2.0)
if (response.isSuccessful()) {
    showToast("명령 성공!");
    finishLoading(targetId, body != null ? body.state : null);
} else {
    finishLoading(targetId, null);   // 요청 전 상태
    showFailure("제어 실패: ", response);
}
무엇을 2xx면 성공, 아니면 실패. 서버 문구를 비교하지 않는다.
왜 문구 비교는 서버가 문구를 바꾸기만 해도 깨진다. 상태코드는 HTTP 표준이라 계약이 짧고 단단하다.
빼면(옛 코드 유지) v2.0 성공 본문에는 message가 없어서, 모든 성공이 "실패"로 보인다.

② 실패 본문 읽기 (ApiError.parse)

JsonElement error = root.getAsJsonObject().get("error");
if (error != null && error.isJsonObject()) {
    JsonObject obj = error.getAsJsonObject();
    return new ApiError(httpCode, stringOrNull(obj, "code"), stringOrNull(obj, "message"));
}
// 앱이 직접 만든 401 등 {"error":"문구"} 모양도 문구만은 읽어 둔다.
String text = error != null && error.isJsonPrimitive() ? error.getAsString() : null;
return new ApiError(httpCode, null, text);
무엇을 error가 객체면 code·message를, 문자열이면 문구만 꺼낸다. 본문이 없거나 JSON이 아니면 code·message 모두 null.
왜 계약에 413은 "본문 모양이 다를 수 있음"이라 적혀 있다. 어떤 본문이 와도 예외 없이 httpCode만은 남겨 상태코드별 문구로 이어 간다.
빼면 깨진 본문에서 Gson 예외가 나 콜백이 죽거나, 빈 토스트가 뜬다.

③ 키 이름과 null 안전 비교

BEFORE
@SerializedName("type")
public String type;
...
if (device.getType().equals("MATTER")) { ... }
AFTER
@SerializedName("protocolType")
public String type;
...
if ("MATTER".equals(device.getType())) { ... }
무엇을 JSON 키만 바꾸고 Java 필드·getter 이름(id, getType())은 그대로 둬서, 이것을 쓰는 화면 코드는 안 고쳐도 된다.
왜 상수를 앞에 두면 getType()이 null이어도 false가 될 뿐 크래시가 나지 않는다.
빼면 키 하나를 놓쳤을 때 대시보드를 그리자마자 NullPointerException으로 앱이 죽는다.

4용어 풀이

  • DTO: 서버와 주고받는 JSON 모양을 그대로 옮긴 Java 클래스.
  • @SerializedName: "이 필드는 JSON의 이 키와 연결"이라고 Gson에 알려 주는 표시.
  • errorBody: Retrofit이 2xx가 아닐 때 본문을 담는 곳. 스트림이라 한 번만 읽을 수 있다.
  • lowerCamelCase: totalCount처럼 첫 단어는 소문자, 다음 단어 첫 글자만 대문자.
  • 폴백(fallback): 원래 값이 없을 때 대신 쓰는 값. 여기서는 상태코드별 앱 문구.

5이해도 질문

  1. 서버가 protocolType 대신 옛 키 type을 보내면 대시보드에는 무엇이 보일까? 앱은 죽을까?
  2. ErrorMessages.describe(response)를 부른 뒤 같은 응답으로 ApiError.from(response)를 또 부르면 어떻게 될까?
  3. 413 응답에 본문이 없으면 화면에는 어떤 문구가 뜰까?
정답 보기
  1. getType()이 null이라 TOGGLE·ENERGY·CHART 위젯이 하나도 안 생긴다(빈 섹션). null 안전 비교라 앱은 죽지 않는다. DtoKeysTest가 이 상황을 미리 잡는다.
  2. errorBody는 이미 읽혀 비어 있으므로 code·message가 null인 ApiError가 나온다. 분기와 문구가 둘 다 필요하면 ApiError.from을 한 번 부르고 describe(ApiError)를 쓴다.
  3. "요청이 너무 큽니다."(fallbackFor(413)).
